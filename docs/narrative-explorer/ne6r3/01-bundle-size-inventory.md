## Deployment measurement

Vercel deployment `dpl_4qr1e4Wa2g2QoMGFf5HSqNYPQNe6` used Python 3.12 and the
NE-6R2 commit above. Its build hook completed and reported a 116,334,592-byte
SQLite index with 687 objects. Vercel then reported:

| Measurement | Vercel-reported size |
|---|---:|
| Bundle before dependency optimization | 353.76 MB |
| Bundle after dependency optimization | 317.82 MB |
| Limit actually enforced for this deployment | 225 MB |
| Required reduction to reach that limit | 92.82 MB |
| Automatic optimization already applied by Vercel | 35.94 MB |

The build ended with `LAMBDA_SIZE_EXCEEDED`. These are the exact rounded values
from the deployment log; Vercel did not expose the function artifact or
per-file byte breakdown. Its deployment-files API returned 404 (`File tree not
found`) for this failed build. The Vercel CLI is not installed in this
workspace, so there is no local `.vercel/output/functions` artifact to inspect.

Vercel's general Python documentation describes a 500 MB standard limit, but
that does not change the 225 MB limit recorded for this deployment. The
deployment log is the relevant measurement for this project and build.

## Local source-plus-index reconciliation

The local tracked input total plus the measured generated index is
196,408,859 bytes (196.409 decimal MB, 187.310 MiB). Comparing that number with
Vercel's rounded 317.82 MB report leaves an arithmetic difference of about
121.41 MB. That difference is **not** a measured dependency total: it can
include the runtime, resolved dependencies, generated bytecode, traced files,
or copies introduced by packaging. The actual Vercel artifact is unavailable,
so no per-component attribution or deployable bundle estimate more precise
than the log total is claimed.

## SQLite allocation audit

The local build used the committed JSON sources and wrote its database under
`/tmp`; tracked repository files were untouched. The resulting file matches
the Vercel build-hook size exactly.

| SQLite measurement | Result |
|---|---:|
| File size | 116,334,592 bytes |
| Page size | 4,096 bytes |
| Page count | 28,402 |
| Free pages | 0 |
| `PRAGMA integrity_check` | `ok` |
| `dbstat` table pages | 55,439,360 bytes |
| `dbstat` index pages | 60,866,560 bytes |
| Other allocated pages not attributed by `dbstat` | 28,672 bytes |

The largest database allocations are the canonical keyword table (26,304,512
bytes), its primary-key autoindex (29,679,616 bytes), the
`idx_keywords_term_type` index (15,233,024 bytes), `canonical_objects`
(14,422,016 bytes), and `idx_keywords_term` (7,593,984 bytes). The keyword
indexes support retrieval and are part of the checked schema contract; no
index was removed. With zero free pages, a `VACUUM` pass has no free-page
reclamation available.
